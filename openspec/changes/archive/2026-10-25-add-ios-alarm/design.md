# Design

## Context

`IosReminderScheduler` (Kotlin, `shared/src@ios`) clears all pending notification requests and adds the soonest 60 as local notifications whose tap reports the entry through `EntryRequests`. `UpcomingReminder` carries the reminder `kind` and the scheduler already reports `supportsAlarms`. Android rings alarms with its own service. The iOS app is `iosApp/src/iosApp.swift` (SwiftUI) hosting the Compose view controller, with an `Info.plist` in the same folder; the Xcode project is generated by Amper (`ios/app`). AlarmKit (iOS 26) is Swift-only: its API is `AlarmManager.shared.schedule(id:configuration:)` with an `.alarm(schedule: .fixed(Date), attributes:, stopIntent:, secondaryIntent:, sound:)` configuration, `cancel(id:)`, the app's own `alarms` list with a state (scheduled, countdown, paused, alerting) and `requestAuthorization()`. The alert has a title and one optional secondary button whose `.custom` behaviour runs an App Intent; the Stop button is the system's. The project's deployment target is iOS 18.2. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Alarm-kind times ring as system alarms on iOS 26+, with Open task and Stop.
- Everything that is not an available, allowed alarm keeps working as a notification.
- Pure routing rules testable in `shared`; the Swift kept thin.

**Non-Goals:**
- Time Sensitive notifications (they need a capability a free Apple account may lack), custom sounds, countdowns, snooze, and the desktop.

## Decisions

- **A Kotlin interface offered by Swift.** `shared` defines `IosAlarmBridge` (is AlarmKit available, current authorization, request authorization with a callback, and `replaceAll(items)` with plain items of entry id, text and epoch milliseconds) and a holder `IosBridge` with a settable `alarms` and a shared `EntryRequests`. Swift implements the protocol, registers it before the first screen is made, and the App Intent hands its entry id to `IosBridge.entryRequests`. Alternative: calling AlarmKit from Kotlin/Native; impossible, it has no Objective-C interface.
- **Routing in shared.** A pure function takes the upcoming times, whether alarms are available and whether they are authorized, and returns the times for alarms (the soonest 20 of the alarm kind, using the existing `AlarmPlan.arm` limit) and the times that stay notifications (all notification-kind times, plus alarm-kind times when alarms cannot be used). `IosReminderScheduler` calls it, sends the first list to the bridge and schedules the second as notifications as today.
- **Replacing the schedule.** The Swift side cancels the app's alarms that are not currently alerting, then schedules each item with a new random id and `.fixed(date)`. Skipping an alerting alarm means an unrelated schedule change cannot cut a ring short. Alarm ids need no mapping because the whole set is rebuilt each time.
- **Open task as an App Intent.** `OpenTaskIntent` conforms to `LiveActivityIntent`, opens the app, takes the entry id as a parameter and calls `IosBridge.entryRequests.open`. It is the alert's secondary button with `.custom` behaviour. The existing `App` collector then switches to Today and reveals the entry. The Stop button is the system's and needs no intent.
- **Metadata.** `AlarmAttributes` is built with a small `AlarmMetadata` carrying the entry id and an accent colour from the app.
- **Permission.** `ReminderScheduler` gains `suspend fun ensureAlarmPermission(): Boolean` (default true) and `TodayViewModel` returns a new `SavedAlarmsOff` result for an alarm when it is false, after the notification permission step. `TemplatesViewModel` emits the matching notice. iOS answers by calling the bridge's `requestAuthorization`; with no bridge (older iOS) it answers true, because the reminder simply falls back to a notification. `NSAlarmKitUsageDescription` is added to `Info.plist`.
- **Older iOS and denied permission.** The Swift bridge reports itself unavailable below iOS 26 (checked with `#available`), and the routing function then keeps alarm-kind times as notifications. A denied authorization does the same.
- **No Widget Extension unless the spike demands it.** The first working slice is built without one. If the alarm does not appear or its button does not work, that is recorded and the design is revisited before more is built; an extension would need a new Xcode target that the Amper-generated project may not support, and an extra App ID on a free account.
- **Spike findings.** Tried on an iPhone with iOS 26.7.1 signed with a free Apple team: the alarm works as the specs describe, including Open task and Stop and the permission prompt, and it was built and run with no Widget Extension, so none is needed for alert-only alarms. The Swift files in `iosApp/src` are compiled by the Amper-generated project without changes to it, and the Kotlin interface and holder are visible to Swift from the shared framework.

## Risks / Trade-offs

- [An alert-only alarm may need a Widget Extension] → The spike tests exactly this first; the tasks stop for a decision if it does.
- [The Amper-generated Xcode project may not accept extra Swift files or an extension] → Swift files in `iosApp/src` are already compiled; the spike checks it, and the build is run after each step.
- [The notification fallback hides a refusal] → The user is told when saving that alarms are off, with where to turn them on.
- [A free Apple account re-signs apps weekly] → Nothing new; AlarmKit needs no entitlement.
- [`replaceAll` runs often] → It only touches alarms that are not alerting and rebuilds a set of at most 20.

## Migration Plan

No data change. On iPhones earlier than iOS 26 nothing changes. Rolling back means routing every alarm to notifications again.
