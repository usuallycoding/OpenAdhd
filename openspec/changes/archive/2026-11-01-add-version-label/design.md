# Design

## Context

See proposal.md for why and the spec delta for behavior. Settings is a `LazyColumn` in `SettingsScreen` whose last item is the `data-delete` row, and `SettingsViewModel` already takes small platform facts as constructor parameters (`dynamicColorSupported`, `loginItem`) that `App.kt` fills from the `AppContainer`. Each platform builds its container in its own factory (`createAndroidContainer(context)`, `createIosContainer()`, `createDesktopContainer()`), which is where platform information is already at hand. Observed versions: the Android APK reports `versionName` "unspecified" and code 1 (the toolchain schema offers `settings.android.versionName` and `versionCode`), the iOS project's `MARKETING_VERSION` is 1.0 and `src/Info.plist` reads it through `$(MARKETING_VERSION)`, and the macOS packaging script passes 1.0.0 to jpackage, which sets the `jpackage.app-version` system property in the packaged app.

## Goals / Non-Goals

**Goals:**
- Show what the installed app really is, not a constant that can drift from the artifact.
- One starting number, 1.0.0 build 1, on every platform.
- The label text and its placement testable without a device.

**Non-Goals:**
- A tool that bumps every place at once, copying the label, an About screen, update checks (see proposal.md).

## Decisions

**1. The version text travels in the container, not through `expect`/`actual`.**
`AppContainer` gets a `versionLabel: String`, and each platform factory computes it from its own source and passes it in; `App.kt` gives it to `SettingsViewModel`. The brief suggested an `expect`/`actual`, but the Android source needs a `Context`, which `shared` has no global access to, so an `actual` would need a context holder just for this. The factories already have the context and are the single place each platform is wired, and tests set the label directly with no injection mechanism of their own. The default for a container built with no label is "OpenAdhd dev".

**2. The label text is built by one helper in shared code.**
`AppVersion.label(name, build)` returns "OpenAdhd 1.0.0 (1)" for a name and build, "OpenAdhd 1.0.0" with no build, and "OpenAdhd dev" when the name is missing or blank. Every platform calls it, so the format is defined and tested once. A build that is missing or blank is left out rather than shown as "()".

**3. Each platform reads its own installed version.**
- Android: `PackageManager.getPackageInfo` for the app's package; `versionName`, and `longVersionCode` from API 28 (`versionCode` before), using the typed-flags overload on API 33 and later to avoid the deprecated call. A failure to read falls back to no version, which shows "dev".
- iOS: `NSBundle.mainBundle.infoDictionary` keys `CFBundleShortVersionString` and `CFBundleVersion`.
- Desktop: `System.getProperty("jpackage.app-version")`, which jpackage sets for the packaged app and is absent when run from the build tool. No build number.

**4. The versions are set where each platform keeps them.**
Android: `settings.android.versionName: 1.0.0` and `versionCode: 1` in `androidApp/module.yaml`. iOS: the literal `1.0.0` and `1` in `iosApp/src/Info.plist`, replacing the `$(MARKETING_VERSION)` and `$(CURRENT_PROJECT_VERSION)` references. The toolchain regenerates `module.xcodeproj` (it reorders and rewrites it on every build), so a value kept in the project file would be lost, while `Info.plist` is hand-maintained already (it holds the alarm usage text). macOS: `scripts/package-mac.sh` already says 1.0.0. Three places to bump by hand, listed in the README; a script that bumps them is out of scope.

**5. The label is one more row at the end of the list.**
A `LazyColumn` item after `data-delete`, outside the Data section's rows: `Text` in the small body style, `onSurfaceVariant` color, centered, with vertical padding so it clears the Delete all data row and the bottom navigation, and no click handling. A test tag lets tests find it.

## Risks / Trade-offs

- [Three version numbers must be bumped by hand and can disagree] → The label shows the truth per platform, so a mismatch is visible instead of hidden; the README lists the three places.
- [The iOS project file still says `MARKETING_VERSION = 1.0` while `Info.plist` says 1.0.0] → The plist literal wins in the built app; the project variable is regenerated by the toolchain and is not worth editing.
- [Android's `versionName`/`versionCode` setting names come from the toolchain schema, not from a working build here] → Checked in the tasks by building the APK and reading its badging.
- [A device where the package info cannot be read] → The label falls back to "OpenAdhd dev" instead of failing to open Settings.

## Migration Plan

None: no stored data changes. The Android build already has version code 1 and only gains a name, so it installs over the previous build and keeps its data. Later releases raise the code as usual.
